What it is

abcdefg is a Claude Code skill that orchestrates a disciplined build process. When you ask to build or ship a non-trivial change, it walks the work through seven phases in order, each a dedicated subskill. The name is the mnemonic for the phase sequence:

Analyze → Blueprint → Construct → Debug → Enhance → Finalize → Go

When to use it

  • Building or shipping a non-trivial feature, fix, or change from request to done.
  • You want a repeatable order that prevents skipping design, testing, or cleanup.

The seven phases

A — Analyze

Understand the request and existing code before any design or code.

  • Restate the request; confirm the desired outcome.
  • Clarify unknowns and acceptance criteria.
  • Locate relevant files and existing patterns.
  • Surface constraints: dependencies, data shapes, edge cases, non-goals.

Exit: the problem and constraints are stated precisely.

B — Blueprint

Design the approach before writing code.

  • Choose the approach; name components and responsibilities.
  • Define interfaces and data flow at the boundaries.
  • List the files to create or change, and in what order.
  • Note trade-offs; reuse existing patterns first.

Exit: a concrete plan — components, interfaces, files, build order.

C — Construct

Implement the blueprint.

  • Build in vertical slices — one working path at a time.
  • Match the surrounding code's style and idioms.
  • Implement to the defined interfaces; note any forced changes.

Exit: the change is implemented and runs.

D — Debug

Make it correct, and record a "before".

  • Run it across the happy path and edge cases.
  • Reproduce failures minimally before fixing; fix root causes.
  • Add or run tests to lock in behavior.
  • Capture a "before" baseline — a screenshot for UI work, or recorded output otherwise.

Exit: behavior verified, tests pass, "before" captured.

E — Enhance

Improve beyond "works", and record an "after".

  • Harden edge cases and failure modes.
  • Tighten error handling and validation.
  • Refactor for clarity; address performance where it matters.
  • Capture an "after" baseline matching the "before" (same viewport/inputs).

Exit: robust and clear, with an "after" to compare.

F — Finalize

The gate — is the original request actually met?

  • Compare the "before" and "after" baselines; confirm the enhancements landed with no regression.
  • Re-check every part of the original request from Analyze.
  • If not fully met → loop back to the earliest affected phase and re-gate.
  • Once it passes: remove dead code, update docs, confirm tests green.

Exit: request verifiably fulfilled; diff tight and green.

G — Go

Ship the change.

  • Commit with a clear message; push to the right branch.
  • Open or merge the PR; confirm CI passes.
  • Report what shipped — link the commit/PR.

Exit: committed, pushed, and on its way to the target branch.

How triggering works

Only the parent abcdefg skill auto-triggers — on requests like "build this feature", "implement X end to end", or "take this from idea to shipped". The seven phases are internal steps it invokes in turn; they don't fire on their own, which keeps a stray "debug this" from launching a lone phase.

Running it locally

Link the repo's skills into your Claude CLI, then trigger the workflow by describing a feature:

scripts/link-skills.sh   # symlink every SKILL.md into ~/.claude/skills
scripts/list-skills.sh   # list all skills in the repo

If a later phase reveals a gap, the workflow returns to the earliest affected phase and continues forward again.
